# Реализованный backend: API и хранение

Запуск и секреты описаны в [operations.md](operations.md), подключение UI — в [frontend.md](frontend.md). Контракт — [OpenAPI](../api/openapi.yaml). Все команды выполняются из корня репозитория.

## Шифрование и схема БД

Пакет `internal/cryptostore` использует AES-256-GCM с nonce, который создаёт Go `NewGCMWithRandomNonce`. Конверт хранит версию алгоритма, версию ключа и ciphertext (nonce + данные + tag). AAD включает тип документа, UUID владельца, версию схемы и ревизию. Пакет поддерживает чтение старой версии ключа и повторное шифрование текущим ключом. Для поиска MAX ID отдельно используется HMAC-SHA256 с собственным lookup-ключом. Все ключи — независимые 32-байтовые значения.

Ключи создаются только в файлах; CLI не выводит их на экран:

```sh
mkdir -p .local/secrets && chmod 700 .local .local/secrets
docker build --target ops -t max-carreer-bot-ops .
docker run --rm --user "$(id -u):$(id -g)" \
  --mount type=bind,src="$PWD/.local/secrets",dst=/secrets \
  max-carreer-bot-ops generate-key -out /secrets/data-key-v1.hex
```

Для lookup-ключа повторите команду с другим именем файла. CLI создаёт файл с правами `0600` и не заменяет существующий. Каталог `.local/secrets/` исключён из Docker-контекста. Не теряйте ключи: без них зашифрованные документы восстановить нельзя.

SQL-миграции `migrations/0001_user_core.up.sql`–`migrations/0004_bot_inbox.up.sql` создают пользовательские таблицы, идемпотентность, каталог и очередь бота. Compose запускает отдельный контейнер миграций до API; повторно применённые файлы пропускаются, изменение уже применённого файла блокирует запуск. Для ранее созданной вручную БД без таблицы `schema_migrations` нужен отдельный перенос состояния; не направляйте новый мигратор на неё без проверки. Down-миграции предназначены только для тестового окружения. Черновик, профиль, избранное и адресат приветствия шифруются перед записью. Ревизия черновика монотонно растёт даже после его удаления, чтобы старый запрос не мог создать новый черновик с прежней ревизией.

## MAX-вход и сессии

`cmd/api` проверяет исходную строку `window.WebApp.initData` по [алгоритму MAX](https://dev.max.ru/docs/webapps/validation), включая дубликаты параметров, URL-декодирование один раз, HMAC и срок 5 минут. Он выдаёт случайный bearer-токен на 12 часов, хранит в БД только SHA-256 токена, проверяет его на каждом запросе и отзывает при выходе. MAX ID в БД представлен HMAC от отдельного lookup-ключа. Реализованные методы описаны в [OpenAPI](../api/openapi.yaml).

Воспроизводимая проверка использует два временных контейнера, синтетический токен бота и двух синтетических пользователей. Нужны Docker, Bash, Python 3, `jq` и `curl`:

```sh
scripts/checks/smoke-api.sh
```

Скрипт проверяет вход, разделение пользователей, черновик, завершение опросника, транзакционный импорт каталога, выдачу, фильтры, избранное, закрытые и исчезнувшие карточки, полный сброс и отсутствие открытых ответов в дампе. Все временные контейнеры, сеть и файлы он удаляет после завершения.

`cmd/api` поддерживает `APP_ENV=local` и `APP_ENV=production`. Для ручного запуска нужны файлы `MAX_BOT_TOKEN_FILE`, `MAX_WEBHOOK_SECRET_FILE`, `IDENTITY_LOOKUP_KEY_V1_FILE`, `DATA_KEY_V1_FILE` и `DATABASE_URL_FILE`, а также миграции по `0004`. Production дополнительно требует публичный HTTPS `PUBLIC_ORIGIN`, включённый worker и настоящий токен. Сам API слушает внутренний порт `8081`, наружу его публикует прокси. Настоящий вход в мобильном и веб-MAX ещё требуется проверить с выданным токеном бота; локальный smoke использует синтетическую подпись.

## Бот MAX

`POST /api/v1/webhooks/max` проверяет `X-Max-Bot-Api-Secret`, принимает `bot_started` и личное сообщение `/start`, сохраняет минимальную зашифрованную задачу и только затем отвечает `200`. Повтор события не создаёт новую задачу. При ошибке БД ответ `503`; тело ограничено 256 KiB. В таблице остаются HMAC события и адресата, а сам ID адресата удаляется после отправки или окончательного сбоя; вся запись удаляется через 48 часов.

Отправку включает `MAX_WORKER_ENABLED=1`; дополнительно задайте `MAX_APP_BOT_USERNAME` для кнопки `open_app`. `MAX_API_BASE_URL` по умолчанию указывает на официальный HTTPS API; пользовательский адрес также обязан быть HTTPS. Образ содержит корневые сертификаты Debian. Если для MAX требуется дополнительный доверенный сертификат, смонтируйте PEM-файл и задайте `MAX_CA_CERT_FILE`; проверка TLS остаётся включённой. Worker отправляет не чаще одного сообщения в две секунды, повторяет сетевые ошибки, 429 и 5xx с задержкой, максимум пять попыток. В локальном smoke worker выключен, чтобы не обращаться к реальному MAX. Формат кнопки и доставку нужно проверить на настоящем боте перед публичным запуском.

## Профиль и черновик

Все методы требуют `Authorization: Bearer <token>`. `GET /api/v1/questionnaire` отдаёт версии банка, направления, профили, шкалу и варианты общих вопросов. `GET /api/v1/me` возвращает `profile`, `draft` и их ревизии; `GET /api/v1/me/draft` — черновик с `revision`.

`PUT /api/v1/me/draft` принимает полный документ и ожидаемую ревизию. При первом сохранении она равна `0`; после отмены редактирования использовать актуальное значение из `GET /me/draft`. Сервер сам вычисляет `question_ids`, версии банка и `base_profile_revision`. Пример:

```json
{"revision":0,"draft":{"current_step":1,"directions":["backend"],"goals":["course"],"education_stage":"undergraduate","study_year":2,"preferred_format":"online","backend_languages":["go"],"skills":{"BACK-01":0}}}
```

`goals`: `course`, `internship`, `event` или отдельно `explore`. `education_stage`: `vocational`, `undergraduate`, `graduate`, `alumni`, `other`, `prefer_not_to_say`. Формат: `online`, `offline`, `both`; для очного участия требуется город или `any_city`. `study_year` допустим только для учащихся, 1–6. На первом шаге можно сохранить ещё пустой выбор направлений. `backend_languages` имеет смысл только при выборе backend. `preferred_cities` проверяются по длине и уникальности; отдельного справочника городов пока нет.

`POST /api/v1/me/onboarding/complete` принимает `{"draft_revision":1}` и обязательный заголовок `Idempotency-Key` со случайным UUID. Одинаковый запрос с тем же ключом в течение 24 часов возвращает прежний результат; другой запрос с тем же ключом получает 409. Завершение требует все ответы и общие поля, атомарно заменяет активный профиль и удаляет черновик. `DELETE /api/v1/me/draft` отменяет редактирование, сохраняя профиль. `DELETE /api/v1/me/data` удаляет аккаунт, профиль, черновик и все сессии. Полный контракт — в [OpenAPI](../api/openapi.yaml).

## Каталог, рекомендации и избранное

`GET /api/v1/recommendations` возвращает активные опубликованные карточки, отсортированные по совпадению направления, цели, условий, опыта, дедлайну и ID. `GET /api/v1/opportunities` поддерживает точные фильтры `type`, `direction`, `format`; `GET /api/v1/opportunities/{id}` показывает опубликованную карточку, в том числе закрытую. Все методы требуют завершённого профиля. Ответ содержит `catalog_version`, `profile_revision`, `ranking_version`, `evaluated_at`; пустой результат фильтра — `200` с `items:[]`. Пока нет активной реальной версии каталога, `/readyz` и выдача возвращают `503`.

`GET /api/v1/me/favorites` возвращает зашифрованное избранное с текущим статусом карточек. Исчезнувшая или снятая с публикации карточка видна только как `id` и `unavailable`; закрытая сохраняет публичные данные со статусом `closed`. `PUT /api/v1/me/favorites/{id}` добавляет только доступную карточку; `DELETE` удаляет ID даже после исчезновения карточки. Повторные PUT/DELETE не увеличивают ревизию. Лимит — 500 ID.

Каталог импортирует отдельная CLI-команда. Ей нужен JSON-файл, применённая миграция `0003`, доступ к PostgreSQL и явный список разрешённых доменов источников. Например, синтетический [тестовый набор](../testdata/catalog-demo.v1.json) можно проверить так:

```sh
docker build --target ops -t max-carreer-bot-ops .
docker run --rm --mount type=bind,src="$PWD/testdata",dst=/fixture,readonly \
  max-carreer-bot-ops catalog validate -file /fixture/catalog-demo.v1.json \
  -allow-domain example.test
```

Для публикации используйте `catalog import` с теми же `-file` и `-allow-domain`, добавив `-database-url-file PATH` и смонтировав файл URL в контейнер. Импорт одной транзакцией активирует новую версию; повтор тех же байтов — no-op, невалидный файл не меняет текущую версию. `is_demo=true` хранится отдельно и не попадает в обычную выдачу. В репозитории пока нет проверенных реальных карточек: синтетический набор предназначен только для тестов. Действующие ссылки и конечные адреса редиректов редактор проверяет вручную перед публикацией; сервер ссылки не обходит.
