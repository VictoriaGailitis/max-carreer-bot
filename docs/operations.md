# Запуск и обслуживание проекта

## Локальный стенд

Из корня проекта выполните `bash scripts/dev/bootstrap-local.sh`, затем `docker compose up --build -d`. Скрипт создаёт только локальные случайные секреты и отказывается перезаписывать существующие. API доступен через Caddy по `http://127.0.0.1:18080`; PostgreSQL доступен только внутри сети Compose. Проверки: `curl http://127.0.0.1:18080/healthz` и `bash scripts/checks/smoke-compose.sh`. Остановка без удаления данных: `docker compose down`.

## Порядок запуска

`db` становится healthy, контейнер `migrate` применяет SQL и выдаёт роль `navigator_api` права на пользовательские таблицы и чтение каталога, затем стартует `api`, после него `proxy`. Применённые версии и SHA-256 файлов находятся в `schema_migrations`. При расхождении контрольной суммы мигратор останавливается. Уже существующую БД с миграциями, применёнными вручную без журнала, нельзя автоматически подключать к этому мигратору: сначала нужно отдельно сверить схему и зафиксировать версии.

Для диагностики: `docker compose ps` и `docker compose logs db migrate api proxy`. `/healthz` подтверждает, что процесс отвечает; `/readyz` требует активную версию реального каталога и до её импорта возвращает `503`.

## Фронтенд

Исходники React frontend находятся в `frontend/`, Go-модуль — в `backend/`. Основной `docker compose up --build -d` собирает frontend через `frontend/Dockerfile` и раздаёт его через Caddy вместе с API. Подключение dev server, локальный тестовый вход и TypeScript-клиент описаны в [инструкции для фронтенда](frontend.md). Необязательный `deploy/compose.frontend.yaml` подменяет встроенную статику заранее собранным `frontend/dist/` с хоста; другой путь задаётся через `FRONTEND_DIST`. При отдельном origin API задайте точный `CORS_ALLOWED_ORIGINS`; production принимает только HTTPS origins.

## Публичное размещение

Сначала настройте DNS домена на сервер, предоставьте настоящий токен бота MAX и настройте URL мини-приложения. В `.env` заполните `PUBLIC_DOMAIN` (только имя домена) и `MAX_APP_BOT_USERNAME`. Замените синтетический `.local/secrets/bot-token` реальным токеном; остальные секреты должны оставаться случайными и неизменными при рестартах. Для боевой БД и пользователей не используйте локальный тестовый набор данных. Запустите `docker compose -f compose.yaml -f deploy/compose.production.yaml up --build -d`. Overlay включает worker и публикацию 80/443; Caddy получает и обновляет сертификат для домена. В MAX настройте подписку на `https://<домен>/api/v1/webhooks/max` с `bot_started` и `message_created`, указав значение из `.local/secrets/webhook-secret`.

Файлы `.local/secrets/` и `.env` не включаются в образ и Git. API подключается к БД как `navigator_api` без DDL и без записи в каталог. Мигратор использует отдельный административный URL только во время запуска. На хосте каталог `.local/secrets/` имеет права `0700`, файлы — `0600`; Compose запускает API и мигратор от UID владельца файлов. Если API MAX требует дополнительный доверенный CA, предоставьте PEM-файл через отдельный read-only mount и `MAX_CA_CERT_FILE`. TLS-проверку не отключайте.

Обычный рестарт: `docker compose restart api` или повторный `up --build -d`; том `db_data` сохраняется. `docker compose down -v` удаляет БД и не является обычной командой остановки. До работы с реальными данными остаются проверка backup/restore вместе с ключами, импорт проверенного каталога и сквозной тест в мобильном и веб-MAX.
