# Курсик — навигатор образовательных возможностей в MAX

## Назначение решения

Курсик помогает студентам и начинающим специалистам оценить свои навыки, выбрать направление развития и найти курсы, стажировки и образовательные мероприятия. MVP включает мини-приложение на React, сервер на Go, PostgreSQL и интеграцию с ботом MAX. Результат опроса — субъективная самооценка, а не экзамен или гарантия готовности к работе.

## Основной пользовательский сценарий

1. Пользователь открывает мини-приложение в MAX и входит через MAX Bridge.
2. Выбирает 1–3 направления, специализации, цели, этап обучения, формат и при необходимости город.
3. Отвечает на вопросы о навыках. Черновик сохраняется на сервере; незавершённый опрос можно продолжить.
4. Завершает опрос и получает качественный результат по направлениям на экране «Твой курс».
5. Открывает каталог, фильтрует возможности, сохраняет карточки в избранное и переходит на сайт организатора.
6. При повторном тесте прежний результат остаётся доступен до завершения нового. В профиле можно выйти или удалить свои данные.

## Состав и архитектура

```text
Браузер / мини-приложение MAX
             │ HTTP локально, HTTPS при публичном размещении
             ▼
proxy: Caddy + собранный React frontend
             │ /api/v1/*, /healthz, /readyz
             ▼
api: Go API + worker бота (выключен локально)
             │
             ▼
db: PostgreSQL ◀── migrate: SQL-миграции перед запуском API
```

| Компонент / каталог | Назначение |
| --- | --- |
| `frontend/` | React, TypeScript, Vite; интерфейс, MAX Bridge, клиентское демо и тесты |
| `backend/cmd/api/` | Авторизация, опросник, профиль, результаты, каталог, избранное, webhook MAX |
| `backend/cmd/migrate/` | Одноразовое применение миграций и настройка ограниченной роли API |
| `backend/cmd/ops/` | Проверка и импорт каталога, служебные операции |
| `backend/internal/` | Прикладная логика, хранение, шифрование, интеграции |
| `backend/data/`, `backend/internal/geography/` | Банк вопросов и общий справочник городов |
| `api/` | OpenAPI-контракт и общий TypeScript-клиент |
| `deploy/` | Caddy и дополнительные конфигурации Compose |
| `scripts/` | Подготовка окружения, проверки, сбор и импорт каталога |

Compose запускает здоровую БД, затем мигратор, API и прокси. Успешно завершившийся `migrate` со статусом `Exited (0)` — нормальное состояние. Frontend собирается внутри Docker и раздаётся Caddy; отдельный Node.js-сервер в рабочем стенде не нужен.

## Окружение и зависимости

Для локального запуска нужны Docker Engine / Docker Desktop с работающей службой Docker, Docker Compose v2, Bash и Python 3.10+ для первичной генерации секретов. На Windows используйте WSL2. Порт `18080` должен быть свободен. При первой сборке необходим доступ к реестрам Docker, npm и Go-модулей.

Для полного API smoke-теста нужны также `curl`, `jq` и свободный порт `18081`. `make` необязателен: команды из [Makefile](Makefile) можно выполнять напрямую. Go и Node.js на хосте для основного Docker-запуска не нужны. Для разработки frontend вне Docker нужен Node.js 22.18+ и npm.

**Файлы фиксации зависимостей присутствуют:**

| Файл | Что фиксирует |
| --- | --- |
| [backend/go.mod](backend/go.mod) | Go 1.27.1, `pgx/v5` 5.11.0 и версии косвенных зависимостей |
| [backend/go.sum](backend/go.sum) | Контрольные суммы Go-модулей |
| [frontend/package.json](frontend/package.json) | React / React DOM 19.2.6, Vite 8.0.13, TypeScript 5.9.3 и остальные прямые зависимости |
| [frontend/package-lock.json](frontend/package-lock.json) | Дерево npm-зависимостей с версиями и integrity; установка через `npm ci` |

Python-скрипты используют стандартную библиотеку; отдельный `requirements.txt` им не требуется. Образы: PostgreSQL 17.11, Go 1.27.1, Node.js 22.18.0, Caddy 2.11.4. Go и PostgreSQL дополнительно закреплены digest в конфигурации; Node.js и Caddy — тегами версий.

## Docker-конфигурация и быстрый запуск

В репозитории есть все необходимые файлы сборки:

- [backend/Dockerfile](backend/Dockerfile) — API, мигратор, CLI и тесты;
- [frontend/Dockerfile](frontend/Dockerfile) — сборка frontend и образ Caddy со статикой;
- [compose.yaml](compose.yaml) — все локальные компоненты;
- [.dockerignore](.dockerignore) и [backend/.dockerignore](backend/.dockerignore) — исключения для двух контекстов сборки;
- [.env.example](.env.example) — пример настроек без рабочих токенов, паролей и ключей.

Все команды ниже выполняются из корня репозитория, если не указано другое.

**Первичная подготовка, один раз:**

```sh
bash scripts/dev/bootstrap-local.sh
```

Скрипт создаёт `.env` с UID/GID текущего пользователя и случайные локальные секреты в `.local/secrets/`. Не копируйте `.env.example` перед bootstrap: при наличии `.env` или `.local/secrets/` скрипт отказывается их перезаписывать. Если окружение уже подготовлено, пропустите этот шаг; частично созданное окружение сначала проверьте вручную.

**Одна команда для сборки и запуска всех локальных компонентов:**

```sh
docker compose up --build -d
```

Откройте **http://127.0.0.1:18080**. Этот адрес раздаёт frontend и API. Production-сборка интерфейса требует входа через MAX; для проверки без MAX используйте API-тесты или режим разработки ниже.

```sh
docker compose ps -a
curl -fsS http://127.0.0.1:18080/healthz
```

Ожидается `{"status":"ok"}`. До импорта реального каталога `/readyz` возвращает `503`: вход, опросник и результаты самооценки при этом доступны.

## Переменные окружения и секреты

Корневая `.env` используется Compose для подстановок; произвольная переменная из неё не передаётся автоматически в API. Настройки API заданы в `environment` соответствующего сервиса.

| Переменная `.env` | Назначение / значение |
| --- | --- |
| `APP_UID`, `APP_GID` | UID/GID для чтения файлов секретов; bootstrap подставляет текущие значения, fallback Compose — `65532` |
| `CORS_ALLOWED_ORIGINS` | Необязательный список точных origins через запятую; пусто для общего адреса frontend/API; production допускает HTTPS |
| `PUBLIC_DOMAIN` | Домен без схемы, обязателен для production overlay |
| `MAX_APP_BOT_USERNAME` | Имя бота, обязательно для production overlay |
| `FRONTEND_DIST` | Только для необязательного overlay с готовой сборкой на хосте; по умолчанию `./frontend/dist` |

| Переменная контейнера | Назначение / локальное значение |
| --- | --- |
| `APP_ENV` | `local`; production overlay задаёт `production` |
| `HTTP_ADDR` | API слушает `0.0.0.0:8081` |
| `MAX_WORKER_ENABLED` | `0` локально, `1` в production; включает отправку сообщений ботом |
| `MAX_API_BASE_URL` | `https://platform-api2.max.ru` |
| `PUBLIC_ORIGIN` | Production overlay формирует `https://${PUBLIC_DOMAIN}` |
| `MAX_CA_CERT_FILE` | Необязательный путь к дополнительному CA для MAX; требует отдельного read-only mount |
| `MIGRATIONS_DIR` | `/migrations` в миграторе |
| `POSTGRES_DB`, `POSTGRES_USER` | `navigator`, `postgres` в контейнере БД |
| `POSTGRES_INITDB_ARGS` | SCRAM-SHA-256 для локальной и сетевой аутентификации PostgreSQL |
| `SITE_ADDRESS` | `:8080` локально; домен в production |

Секреты передаются файлами Docker Compose secrets, а не в коде или frontend. Таблица показывает соответствие переменных файлам на хосте; внутри контейнеров используются пути `/run/secrets/...`, заданные в Compose.

| Переменная | Файл в `.local/secrets/` | Назначение |
| --- | --- | --- |
| `POSTGRES_PASSWORD_FILE` | `db-admin-password` | Пароль администратора БД |
| `DATABASE_URL_FILE` у мигратора | `database-url-migrate` | Административное подключение для миграций |
| `DATABASE_URL_FILE` у API, `APP_DATABASE_URL_FILE` у мигратора | `database-url-api` | Подключение ограниченной роли `navigator_api` |
| `MAX_BOT_TOKEN_FILE` | `bot-token` | Синтетический `local-only-*` локально; настоящий токен для MAX |
| `MAX_WEBHOOK_SECRET_FILE` | `webhook-secret` | Проверка входящих событий MAX |
| `IDENTITY_LOOKUP_KEY_V1_FILE` | `lookup-key` | Независимый ключ HMAC для поиска пользователя |
| `DATA_KEY_V1_FILE` | `data-key` | Ключ шифрования пользовательских документов |

Ключи — по 32 байта в виде 64 hex-символов. Bootstrap создаёт каталог секретов с правами `0700`, файлы — `0600`. `.env` и `.local/` исключены из Git и Docker-образов. Сохраняйте ключи при повторном запуске: новые ключи не расшифруют существующую БД.

## Внешние сервисы и условия проверки

**MAX нельзя воспроизвести внутри Docker.** Он обеспечивает личность пользователя, запуск мини-приложения, Bridge и доставку сообщений бота. Для полного сценария нужны аккаунт MAX, зарегистрированный бот с настоящим токеном, настроенный URL мини-приложения, публичный HTTPS-домен и доступ к API MAX и `https://st.max.ru/js/max-web-app.js`.

Для публичной проверки подготовьте отдельное окружение с реальными секретами, заполните `PUBLIC_DOMAIN` и `MAX_APP_BOT_USERNAME`, направьте DNS на сервер и откройте порты 80/443. Запуск:

```sh
docker compose -f compose.yaml -f deploy/compose.production.yaml up --build -d
```

В MAX настройте webhook `https://<домен>/api/v1/webhooks/max` для `bot_started` и `message_created` с секретом из `.local/secrets/webhook-secret`. Worker включается production overlay. Подробности — [эксплуатация](docs/operations.md). Локальный синтетический токен не подходит для общения с настоящим MAX.

**Публичные сайты VK** используются только при ручном наполнении каталога и переходе к организатору. Для `make seed-vk` нужен сетевой доступ к источникам VK Education и VK Internship. Существующий импортированный каталог хранится в БД; постоянное соединение с VK для выдачи карточек не нужно. Сбор зависит от доступности и структуры внешних страниц.

**Реестры зависимостей и сертификаты:** первая Docker-сборка скачивает образы и библиотеки; публичный Caddy получает TLS-сертификат через ACME. Это инфраструктурные зависимости. Проверка серверной логики с синтетическими данными после загрузки зависимостей не требует MAX или сайтов VK.

## Работа с данными

PostgreSQL хранит пользователей, сессии, профиль, черновик, избранное, версии каталога, записи идемпотентности и очередь бота. Профиль, черновик, избранное и данные адресата бота шифруются AES-256-GCM до записи. Для поиска по MAX ID используется HMAC-SHA256 с отдельным ключом; bearer-токен в БД хранится в виде хеша. В браузере bearer находится только в памяти.

Сохранение черновика проверяет ревизию; устаревшая запись получает `409 REVISION_CONFLICT`. Завершение опроса с `Idempotency-Key` атомарно заменяет профиль и удаляет черновик. Повтор того же запроса возвращает прежний результат. Удаление через экран данных/приватности или `DELETE /api/v1/me/data` удаляет пользовательские данные и сессии.

Каталог импортируется с валидацией и атомарной сменой активной версии. Повтор того же файла не создаёт новую версию; невалидный импорт оставляет прежний каталог. Синтетические карточки `is_demo=true` исключаются из обычной выдачи. При исчезновении карточки избранное сохраняет её ID со статусом `unavailable`.

Данные БД живут в именованном томе `db_data`, данные Caddy — в `caddy_data` и `caddy_config`. `docker compose down` их сохраняет. Резервная копия БД требует сохранения соответствующих ключей отдельно от Git. Формат данных и правила API: [docs/api.md](docs/api.md), [OpenAPI](api/openapi.yaml).

## Тестовые данные

Есть три независимых режима проверки:

1. **Серверный синтетический сценарий:** `make smoke` использует [backend/testdata/catalog-demo.v1.json](backend/testdata/catalog-demo.v1.json), двух тестовых пользователей и отдельную временную БД. Скрипт проверяет исключение demo-каталога, затем только внутри тестового окружения создаёт вариант для обычной выдачи. Ссылки `example.test` вымышленные. Скрипт удаляет свои контейнеры, сеть и временные файлы по завершении; основной стенд не изменяется.
2. **Демо интерфейса:** Vite dev server предлагает «Открыть демо без MAX». Данные находятся в памяти, запросов к backend нет, перезагрузка всё сбрасывает. Демо не проверяет серверную интеграцию и исключено из production-сборки.
3. **Локальный каталог из публичных источников:** после bootstrap выполните `make seed-vk` (или `bash scripts/seed/vk.sh`). Выгрузка и отчёт появятся в `.local/catalog/`; каталог активируется в локальной БД. Сборщик разрешён только с `local-only-*` токеном. Перед публичным использованием нужна редакционная проверка карточек.

Повторный импорт сохранённой выгрузки без нового сбора:

```sh
bash scripts/seed/vk.sh --file .local/catalog/vk.json
```

Импорт заменяет активный каталог целиком. Подробнее: [порядок работы с VK](docs/seed-vk.md).

## Пошаговый сценарий проверки

### 1. Проверить сборку и инфраструктуру

После bootstrap и запуска из раздела выше:

```sh
docker compose config --quiet
docker compose ps -a
curl -fsS http://127.0.0.1:18080/healthz
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/readyz
bash scripts/checks/smoke-compose.sh
```

Ожидается frontend по адресу `http://127.0.0.1:18080`, `200` для `/healthz`, `503` для `/readyz` без каталога. `smoke-compose` проверяет вход, повтор миграций, права роли API и сохранение сессии после рестарта API. Он создаёт синтетического пользователя `987654321` в локальной БД и кратковременно перезапускает API; используйте стенд с `local-only-*` токеном и не проходите опрос под этим служебным ID.

### 2. Проверить серверный пользовательский сценарий без MAX

```sh
make test
make smoke
make check-seed
```

`make test` запускает Go-тесты, `go vet` и проверку форматирования в Docker. `make smoke` проверяет авторизацию, webhook, опросник, черновик, завершение, результаты, каталог, рекомендации, избранное, изоляцию пользователей и удаление данных. Успех заканчивается строкой `MAX auth and webhook, encrypted state and bot inbox, catalog import, ranking, reset and isolation: ok`. `make check-seed` проверяет сборщик без сети.

### 3. Проверить интерфейс без MAX

Для этого необязательного режима установите Node.js 22.18+, затем в отдельном терминале:

```sh
cd frontend
npm ci
npm test
npm run build
npm run dev
```

Откройте `http://127.0.0.1:5173`, выберите «Открыть демо без MAX», пройдите опрос, откройте «Твой курс», каталог и избранное. После обновления страницы демонстрационные данные сбросятся.

Для проверки того же интерфейса с настоящим локальным backend оставьте Docker-стенд запущенным, импортируйте каталог через `make seed-vk` и из корня проекта получите синтетический вход:

```sh
python3 scripts/dev/local-init-data.py
```

На dev-экране входа откройте «Локальный вход для разработки», вставьте **только значение `init_data`** из JSON и нажмите вход. Строка действует 5 минут. Пройдите опрос, сохраните карточку в избранное, обновите страницу и выполните свежий локальный вход: профиль и избранное должны восстановиться с сервера. Dev proxy направляет `/api` на Docker-стенд. Секрет бота в интерфейс не вводится.

### 4. Проверить готовность каталога и интеграцию MAX

После успешного `make seed-vk` проверьте `curl -fsS http://127.0.0.1:18080/readyz`: ожидается `200`. Затем в отдельном публичном окружении, настроенном по разделу внешних сервисов, откройте мини-приложение внутри MAX и повторите основной пользовательский сценарий. Это отдельная проверка: синтетические тесты не подтверждают работу реального MAX.

## Примеры ожидаемого поведения

| Действие / состояние | Ожидаемый результат |
| --- | --- |
| Запрос `/healthz` после запуска | `200`, `{"status":"ok"}` |
| Запрос защищённого API без сессии | `401` |
| Каталог ещё не импортирован | `/readyz` — `503`; рекомендации для завершённого профиля — `503 CATALOG_UNAVAILABLE` |
| Результаты при готовом профиле без каталога | Самооценка доступна; ошибка курсов не должна скрывать результат |
| Сохранение с устаревшей ревизией | `409 REVISION_CONFLICT`, UI предлагает загрузить серверную версию |
| Повтор завершения с тем же ключом и телом | Прежний результат без повторного изменения профиля |
| Фильтр без подходящих карточек | `200` и `items: []` |
| Закрытая / исчезнувшая карточка в избранном | `closed` / `unavailable`; исчезнувшая имеет `item: null` |
| Рестарт API с сохранённой БД и ключами | Профиль и действующая серверная сессия сохраняются |
| Удаление данных пользователя | `204`; прежняя сессия больше не действует |

## Известные ограничения

- Production-интерфейс требует MAX. Демо и синтетический вход доступны только на Vite dev server.
- Полный сценарий с реальным MAX, публичным backend и доставкой сообщений требует отдельной проверки с рабочим ботом.
- Каталог обновляется вручную; административного интерфейса компаний нет. Классификация импортированных карточек требует редакционной проверки, сроки и доступность нужно уточнять у организатора.
- Нет автоматического слияния конфликтующих черновиков; UI предлагает загрузить серверную версию. Отмена черновика через `discardDraft()` пока не подключена в UI.
- Подтверждение изменения набора вопросов ещё не реализовано. Самооценка не заменяет объективную проверку навыков; трекера привычек и гарантированного перехода к стажировке нет.
- Для публичного использования нужны утверждённая политика приватности, выбор лицензии проекта, проверка backup/restore и сквозные проверки в мобильном и веб-клиенте MAX.
- Старую БД с вручную применёнными миграциями без `schema_migrations` нельзя автоматически подключать без сверки схемы.

## Остановка и повторный запуск

Остановить все локальные компоненты с сохранением данных:

```sh
docker compose down
```

Повторно запустить, при необходимости пересобрав код:

```sh
docker compose up --build -d
```

Повторный bootstrap не нужен. Для краткой остановки без удаления контейнеров используйте `docker compose stop`, затем `docker compose start`. Для отдельного рестарта API — `docker compose restart api`. Изменения `.env` применяйте через `docker compose up -d`, а изменения кода — через `up --build -d`.

Диагностика:

```sh
docker compose logs --tail=100 db migrate api proxy
```

`docker compose down -v` **удаляет данные томов**, включая БД, и используется только для намеренного полного сброса тестового стенда. Секреты на хосте эта команда не удаляет. При работе с production или другим overlay указывайте тот же набор `-f`, что и при запуске.
