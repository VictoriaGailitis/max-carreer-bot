# Навигатор возможностей

Общий репозиторий мини-приложения MAX. Сервер реализован в `backend/`; `frontend/` подготовлен для последующего добавления интерфейса. Контракт API, документация и конфигурация запуска общие для обеих частей.

Backend включает вход, опросник, зашифрованные профиль и черновик, каталог, рекомендации, избранное и бот. Сборка и PostgreSQL запускаются через Docker; установленный на хосте Go не используется.

## Быстрый запуск

Нужны Docker с Compose, Bash и Python 3. Для интеграционного smoke также нужны `curl` и `jq`.

```sh
make bootstrap
make up
curl -fsS http://127.0.0.1:18080/healthz
```

Bootstrap выполняется один раз: создаёт `.env` и `.local/secrets/`, отказывается перезаписывать их. Повторный запуск стенда — `docker compose up --build -d`. API доступен на **http://127.0.0.1:18080**, база — только внутри Docker. Worker в локальном режиме выключен.

```sh
docker compose ps
docker compose logs migrate api proxy
docker compose down
```

Остановка сохраняет данные. Ключи шифрования нужны для восстановления БД; храните их вместе с резервной копией отдельно от Git.

## Подключение фронтенда

- [Пошаговая интеграция и локальный вход](docs/frontend.md).
- [OpenAPI 3.1](api/openapi.yaml) — структуры запросов, ответов и ошибок.
- [TypeScript-клиент](api/client/client.ts) — без зависимостей, токен хранится в памяти.
- [Compose для собранного фронтенда](deploy/compose.frontend.yaml) — Caddy отдаёт SPA и API на одном адресе.

По умолчанию используйте `/api/v1` через тот же origin или dev proxy. Для отдельного origin есть точный список `CORS_ALLOWED_ORIGINS` в `.env.example`.

## Проверки

```sh
make test           # go test + go vet + проверка gofmt в Docker
make smoke          # полный API-сценарий в отдельной временной БД
make smoke-compose  # проверка запущенного Compose, миграций и сохранения сессии
make check-client   # TypeScript strict; нужен tsc в PATH
```

Команды доступны и без Make: см. [Makefile](Makefile). `smoke-compose` предназначен для локального стенда с синтетическим токеном. Изолированный `smoke` сам удаляет созданные контейнеры, сеть и временные файлы.

## Структура

```text
backend/           Go-модуль, Dockerfile, SQL, банк вопросов и тесты
frontend/          место для будущего frontend-проекта
api/               общий OpenAPI-контракт и TypeScript-клиент
deploy/            Compose overlays и конфигурация Caddy
docs/              документация полного проекта
scripts/           dev-инструменты и интеграционные проверки
compose.yaml       общий локальный стенд
Makefile           команды из корня репозитория
.env.example       несекретный пример общих настроек
.local/            локальные секреты и временные материалы, вне Git
```

Go-код, `go.mod`, `go.sum`, SQL-миграции, данные и Dockerfile находятся в [backend/](backend/README.md). Будущий интерфейс пушится в [frontend/](frontend/README.md) в том же репозитории. Каждая часть хранит собственные зависимости и настройки сборки; команды Compose и локальные секреты остаются в корне.

Frontend пока не добавлен. После его сборки в `frontend/dist/` используйте `make up-frontend`; стандартный `make up` запускает серверный стенд. Путь к сборке можно изменить через `FRONTEND_DIST` в корневой `.env`.

## Состояние

Unit/API-проверки выполняются с синтетическими пользователями и каталогом. В репозитории нет проверенного реального каталога: до его импорта `/readyz` возвращает `503`, выдача после заполнения профиля — `CATALOG_UNAVAILABLE`. `is_demo=true` не попадает в обычную выдачу.

Для production остаются настоящий токен и настройка MAX, реальные карточки, домен, проверка backup/restore и сквозной сценарий с фронтендом внутри MAX. Порядок размещения — в [runbook](docs/operations.md). Лицензия проекта и условия использования исходных материалов пока не выбраны владельцем.
